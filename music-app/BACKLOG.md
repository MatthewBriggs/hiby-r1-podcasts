## Scanner: why tracks go missing

The stock scanner's path field is **256 bytes**. Measured against the card:
every indexed file has a path of 255 characters or fewer; every music file it
missed is 256 or more. There is no overlap, so this is a hard buffer limit, not
a corruption or a timing problem — 76 tracks across the long-titled classical
sets were simply never seen, and "Update database" would not have helped.

The other 99 files it skips are `._` AppleDouble sidecars left by copying on a
Mac. Skipping those is correct; this app skips them too.

**Since fixed by renaming:** 94 files clipped, over-long files down from 76 to
**24**. The remaining 24 are over the limit because of their *folder* paths, so
the filename alone cannot save them. The mapping is at
`hiby-fw/restore-point/rename_plan_20260801.tsv` and every rename is reversible.

**Still open:** the index holds the 94 files under their old names, and those
rows are dead until a real rescan. The app skips rows whose file has gone and
the per-album folder sweep picks the files up under their new names, so albums
look right — but by sweep, not by index.

The dual `kernel`/`kernel2` and `rootfs`/`rootfs2` partitions make an A/B failover scheme plausible, but **there is no direct evidence yet that u-boot (`mtd0`) actually can or does choose between the two banks** — that would need either u-boot console access (a real serial console exists per `/proc/cmdline`'s `console=ttyS2,3000000n8`, just not hardware this investigation has) or dumping and analysing `mtd0` itself, neither done yet. **Net effect on the original question**: less catastrophic than originally feared, but not resolved. If the large-payload write goes through generic block-device I/O rather than something baked uniquely into `hiby_player`, the low-level *mechanism* isn't lost by replacing `hiby_player` — but `hiby_player`'s UI is still the only thing that currently knows how to find a `.upt` on the SD card, verify it, and drive that mechanism at all; nothing yet says a standalone replacement would need to fully reimplement that specific flow rather than something equivalent, and nothing yet confirms a botched write is actually recoverable via bank fallback rather than just "less immediately catastrophic before you find out it isn't." Next step, if this stays a priority before anything more permanent: find a way to read `mtd0`'s own logic (dump + strings at minimum; real u-boot console access if a serial cable is ever in reach) rather than guessing further from the rootfs side.

**Resolved, 2026-08-16, from a second, independent, working prior-art project.** `github.com/Starnished66/R1-open-source-player` (GPLv3, LVGL, "fully usable on real R1 hardware" per its own README — further along than `open_hiby_player`, closer in spirit to what these RP items are scoping) ships `src/core/firmware_update.c`. It does **not** reimplement low-level flashing at all: `firmware_update_scan()` finds a `.upt` on the SD card exactly like the stock UI does, and `firmware_update_enter_recovery()` is four lines — run `/usr/bin/bootmode.sh Recovery`, then `reboot`. That's the whole mechanism on their side. Checked what `bootmode.sh` actually does **directly on our own device** (this is HiBy's own stock script, not their code): its `Recovery` case is `flash_erase /dev/mtd5 0 1` then `nandwrite`s the literal text `ota:kernel2` into it; its default case writes `ota:kernel` instead — exactly the same `mtd5` partition and exactly the same `flash_erase`/`nandwrite` pair already found in `hiby_player`'s own strings above. **This closes the loop**: `mtd5` is a boot-target flag, `kernel`/`kernel2` name the two banks (`mtd1` vs `mtd3`, and by extension `rootfs`/`rootfs2`), and choosing between them is u-boot's job at the next boot, triggered by nothing more than this tiny flag write plus a reboot. Confirms the A/B scheme is real and does fail over — this was the one piece static analysis alone couldn't prove.

**What this means for "replacing `hiby_player`": the fear was overstated.** The recovery trigger is `flash_erase`+`nandwrite` (ordinary system utilities, not unique to `hiby_player`) plus a plain reboot — four lines any replacement can call directly, already proven working by a second, independent, real-hardware-tested project. **Still open**: exactly how a *new* `.upt`'s multi-megabyte payload gets written into the currently-inactive bank in the first place (this script only flips the flag to fall back to whatever is *already* in the other slot — it doesn't populate it), and whether `mtd0` (u-boot) has any failure mode of its own that isn't bank-dependent. Neither blocks the conclusion that the *recovery* path specifically survives `hiby_player` going away, which was RP3's actual question. |

| W7 | **Shrink the `sa_hgl_dma` graphics pool from 6 MB — potential ~6 MB RAM win, parked** | Full write-up: [NOTES-kernel-optimisation.md](NOTES-kernel-optimisation.md). `sa_hgl_dma.ko` (HiBy's DMA blitter, used by stock `hiby_player`, not by our app's own draw path) reserves **6 MB** via the module parameter `sahd_hgl_mem_size` for a screen whose entire framebuffer is 768 KB — eight screens' worth of scratch, on a device with only ~1.5 MB free at rest. Measured live 2026-08-15: `MemAvailable` is **19,840 kB with the pool open vs 26,336 kB closed** — a real, reproducible **~6.2 MB delta**. The pool is opened once by `hiby_player` at boot and held for its whole lifetime, **including while our Library app is running** (it's a hook inside `hiby_player`, so it inherits the same fd — verified `count=1` with our Main Menu on screen). Recovering even half of this would roughly double the device's current free-memory headroom. **Parked, not abandoned, because testing it needs a flash**: the parameter is runtime-writable (`perm=0644` in `.modinfo`) but the allocation happens lazily in `sahd_open()`, and `killall hiby_player` cannot be used to test a new value — after a restart the player never reopens `/dev/sa_hgl_dma` at all (almost certainly the known graphics-DMA leak leaving `dma_request_channel` failing on reopen), so the sysfs value has to be set *before* the player starts at boot to actually be exercised. That means either editing `sahd_hgl_mem_size=6291456` directly in `sa_hgl_dma.sh` inside the firmware image, or adding a small init script between `S11module_driver_default` and `S92_03_start_music_player` that writes the sysfs value — the same injection mechanism `patch_firmware.py` already uses for `S90adb`. If `hiby_player` is ever dropped in favour of our own app (see W6's note on the same point), this 6 MB is recoverable outright with no tuning needed at all. |
