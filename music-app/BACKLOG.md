## Scanner: why tracks go missing

The stock scanner's path field is **256 bytes**. Measured against the card:
every indexed file has a path of 255 characters or fewer; every music file it
missed is 256 or more. There is no overlap, so this is a hard buffer limit, not
a corruption or a timing problem — 76 tracks across the long-titled classical
sets were simply never seen, and "Update database" would not have helped.

The other 99 files it skips are `._` AppleDouble sidecars left by copying on a
Mac. Skipping those is correct; this app skips them too.

**Since fixed by renaming:** 94 files clipped, over-long files down from 76 to
**24**. The remaining 24 are over the limit because of their *folder* paths, so
the filename alone cannot save them. The mapping is at
`hiby-fw/restore-point/rename_plan_20260801.tsv` and every rename is reversible.

**Still open:** the index holds the 94 files under their old names, and those
rows are dead until a real rescan. The app skips rows whose file has gone and
the per-album folder sweep picks the files up under their new names, so albums
look right — but by sweep, not by index.

| # | Item | Notes |
|---|---|---|
| H1 | Strip the last of the keypress logging | Stays only until the headset's skip codes are known (U2); the output-loss and write-failure lines should stay for good, since they are how a silent failure gets diagnosed. |
| H2 | Second `DEV_HOOK` in `patch_firmware.py` | The music hook chain-loads the podcast hook from `libpodcast_hook.so.real`. That works and needs no flash, but a firmware with two preload slots would be tidier. |
| H3 | M4A seek granularity | Seeking rounds to the start of an access unit, about 23 ms at 44.1 kHz. Fine in practice; recorded so it is not rediscovered as a bug. |
| H4 | **Progressive JPEG cover art is refused, by design** | Turned out to be two of the three: Baltic and Blue Mars both carry progressive 2400×2400 covers, 4:2:0 subsampled — Y at full res plus two quarter-res chroma planes puts the real coefficient-array cost at ~16.5 MB, not the 34.5 MB a naive 3-channel-at-full-res estimate says. Either way it is well past `cover.c`'s 8 MB budget, and correctly so: this device already lost `hiby_player` to the OOM killer twice, once from exactly this. `scale_denom` cannot reduce it — the coefficient array is built at full resolution before any scaling happens. **Worked around for these three books**: re-encoded each embedded cover as baseline with `ffmpeg` (same pixels, no re-download, no quality loss — Baltic and Blue Mars checked side by side against the originals) and dropped the result in as `cover.jpg` beside the `.m4b`, which `art_for_track()`'s loose-file check already tries before touching the embedded picture, so no code changed. Not a general fix — the next progressive-covered book still needs the same by-hand step, or a real one: a decoder that can stream progressive scans (none available on-device), or a hand-rolled DC-only progressive thumbnail decoder (real Huffman/zigzag/MCU work, parsing untrusted input — a project of its own, not attempted here). |
| H6 | **The page-cache trim only covers MP4/M4B, not FLAC** | `mp4.c` drops what is behind the read cursor every ~512 access units, which is what keeps an eleven-hour audiobook from filling RAM (see the framebuffer DMA note in the audiobook commit). FLAC goes through `drflac_open_file()`, which exposes no fd, so a 372 MB hi-res FLAC still fills the page cache unchecked — the same fragmentation exposure that made `hiby_player`'s order-11 (8 MB) contiguous DMA allocation fail and bring the panel up dead. Fixing it means opening FLAC via `drflac_open` with our own read/seek callbacks so the fd is reachable. Not urgent — measured 15 MB still available while streaming the 96/24 album — but it is the same class of bug, only unfixed. |
| H7 | **On `snd_pcm_open` failure the queue is raced through, not stopped** | Seen live 2026-08-07 when the stock player still held the DAC: our app could not open ALSA, and `was_active && !audio_is_active()` fired every tick, so `play_index(cur_track + 1)` walked the entire album in seconds, logging a failure for each. It should stop and surface "no output" once, the way the output-lost path already pauses rather than skipping. |

| W2 | **SoC suspend — sequence recovered from stock, not yet implemented** | **Do not write `mem` to `/sys/power/state` cold: it hangs this device.** Tried live 2026-08-08 with an RTC wakealarm armed and *verified* in the future (guarded so it would refuse to suspend otherwise). The panel blanked, the backlight stayed lit, and nothing brought it back — not the power button, not the RTC alarm at +40s, not a host-side `adb kill-server`. Backlight-on-but-black is the tell: the sequence got as far as blanking the display and then stalled, so it never reached a state any wake source could act on. That is a hang *inside* suspend, not a sleep we failed to wake from. Cost two hard reboots to establish. **The stock 1.6 player does it properly, and the order is recoverable** — `strings usr/bin/hiby_player` (binary order ≈ source order) gives: `PM: sleep` → `PM: early suspend` → `PM: sd0_msg %s` → `/usr/bin/bt_suspend` → `PM: suspend` → `echo mem > /sys/power/state` → `PM: resume` → `PM: late resume` → `/usr/bin/bt_resume` → `PM: sleep out`.
